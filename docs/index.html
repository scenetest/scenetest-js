Scenetest

Evaluate your product, not your tests.

Scenetest started out trying to fix what was wrong with end-to-end testing, but we came to believe that this wasn't what we really wanted. What we love about end-to-end tests is th ability to automate the actions of a user, and then monitor that session and test our expectations about exactly what is updating where and when.

It's time we had tooling that can do more than click around and refresh the page. If we were designing a test framework from first principles in 2026, actually – yes, we would need something to click around with. But then, throughout that journey (or Scene, as we call it) we would want to be able to say "well at this point the database and the local cache and also the component state should all agree.

This is how Scenetest came about: assertions are basically server actions, you write them inside your react app, you fire them inside the react lifecycle, and you pass them values directly from the react context, but the actual comparison functions are bundled on the server and run with access to your database and other resources, giving you the power to test just about any piece of state in any store in your entire sytem.

* * *

A Scene is a user journey. Log in, navigate to settings, change your username, submit the form, see the success message. Scenes are about orchestration—driving the browser through a sequence of interactions. The person writing a Scene shouldn't need to know how the app works under the hood. They just need to know what a user would do.

An Inline Assertion lives inside your application code—in your components, hooks, and callbacks. It validates your mental model: "at this point in the React lifecycle, this data should be in this state." Inline assertions fire whenever the code runs, regardless of who or what is driving the browser.

The insight is that these two dimensions are orthogonal. You can write fifteen different Scenes that all pass through the same component, and each one will run the same Inline Assertions. You can have a QA person improvise edge cases while assertions validate the system automatically. You can even just use your app normally during development and watch the assertions fire.

Assertions at exactly the right moment

Scenetest assertions run inside your components. No extra tooling to run your hooks in a test environment. No recreating your app's logic in a spec file. You write the assertion where the code lives, with access to the real data: 

import { pass, fail } from 'scenetest'

export function ProfileForm() {
  const { data: profile } = useProfile()

  // Runs every render, with the actual value, at the actual moment
  pass('Profile available without loading state', profile !== undefined)

  if (!profile) return <CreateProfileForm />
  return <EditProfileForm profile={profile} />
}

In dev and test mode, these assertions report to a collector. In production, the Vite plugin strips them out entirely. Zero runtime cost.

Multi-context comparisons

The most powerful use case is comparing data across contexts. After a form submission, you might want to verify that the DOM, component state, React Query cache, and database all agree: 

onSuccess: (savedProfile) => {
  const domName = displayRef.current?.textContent
  const stateName = name.trim()
  const cacheName = queryClient.getQueryData('profile')?.name
  const dbName = getProfileFromDb().name

  pass('All contexts agree on name',
    domName === stateName &&
    stateName === cacheName &&
    cacheName === dbName
  )

  fail('Cache out of sync with database',
    cacheName !== dbName
  )
}

This runs inside your onSuccess callback, at exactly the moment when your mental model says everything should be in sync. If there's a bug where the cache updates but the DOM doesn't, you'll catch it here—not in a test file that's trying to reconstruct this moment from the outside.

The Scene stays clean

Because assertions live in the application code, Scene files can focus purely on orchestration: 

test('User updates their profile', async ({ scenePage }) => {
  await scenePage.goto('/profile')
  await scenePage.getByLabel('Name').fill('New Name')
  await scenePage.getByRole('button', { name: 'Save' }).click()

  // That's it. All the assertions fired automatically.
  expect(scenePage.failed).toHaveLength(0)
})

The person writing this Scene doesn't need to know about React Query, or localStorage, or what the component's internal state looks like. They just need to know what a user would do. The implementation experts write the assertions; the journey experts write the Scenes.

What we're really testing

Scenes test the user's experience: does the product work the way we intended?

Inline Assertions test the engineer's mental model: does the system work the way we think it works?

These are complementary questions. A Scene can pass while assertions fail—the user got the right outcome, but through a code path we didn't expect. Assertions can pass while a Scene fails—all our assumptions are correct, but the user can't actually complete the journey because of a UI problem.

Together, they give you a complete picture. You traverse your product along both axes, and you know not just that it works, but why.
