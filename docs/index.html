Scenetest

Local-First testing framework for Vite that evaluates your product, and your mental model – not your tests.

It's 2026; we builds app differently now. Component state, Query cache, Zustand store, Tanstack/DB, Electric SQL, DuckDB in WASM with React bindings... the Local First possibilities are endless, and they're helping us build buttery smooth, responsive UIs.

Test tooling should keep up.

Most frameworks rely on a headless browser clicking around our app, inputting inputs into inputs and clicking clickers and expecting to see certain expectations. If we're being very thorough we might check the database directly to be sure something updated (for certain).

The DOM and the Database are good book-ends to compare, but if the main data store my app relies on is a local DB or store or cache, how will we test this? When we live and die by the rule UI = f(state), testing local state feels like it should be easier…

This is how Scenetest JS came about. We were looking for tests that would:

  1. Compare data we take from inside the React component lifecycle – in onSuccess callbacks, in effects, hooks.
  2. Compare to what we expect to find in the database or other privileged resources.
  3. Write both with full type safety, intellisense, etc.
Thankfully, in 2026 React world, we have a primitive that matches this pattern neatly: Server Actions, which are written in the app, stripped by the bundler, deployed on the server as an RPC function, and called remotely from the client. This inversion of control solves the multi-context app⇔server problem, giving the app control over when to call the server function and what data to pass it, but actually running it in a protected environment. Apply this pattern to a testing framework, and we get a powerful tool for testing our expectations about nearly every layer of an application in one place. 

cost post = usePost(id)
const form = usePostForm(post)
// useAssert is like sugar for useEffect(() => assert(), deps)
useAssert(
  () => {
    title: 'Server item should match local',
    // app data we pass from react-land to the assertion fn
		appData: () => postsCollection.get(id),
    // the assertFn runs on the server as a server action
		assertFn: (server, app) => {
      const post = await server.getPosts(app.id)
      fail('title is empty', !post)
      pass('titles match', post.title === app.title)
    },
    // skip when submitting, run when only finished
    enabled: !form.isSubmitting,
  },
  [form.isSubmitting, post.title]
)

Scenes and Inline Assertions

Scenes are small user journeys, or the sort of atomic units of a user flow you want to test. e.g. scenetest/profile-update.scene.ts: Log in, navigate to settings, change your username, submit the form, see the success message. Scenes are about orchestration – driving the browser through a sequence of interactions. The person writing a Scene shouldn't need to know how the app works under the hood. They just need to think through what sorts of things a user might do or expect.

Inline Assertions are test statements that live inside your application code – in your components, hooks, and callbacks. They validate your mental model: "at this point in the code / React lifecycle, this data should be in this state." Engineers write them to encode and record their mental model and to alert future generations. Use pass or fail, or assertions that run on the server assert and useAssert.

Moving Assertions into the application code means they're type-safe, they run passively even as you just click around, and you never have to write window.__testData?.profileStore = profileStore ever again. And it means your Scenes can be written with any old tool, by a PM, an LLM, etc.

Scenetest assertions run inside your components. No extra tooling to run your hooks in a test environment. No recreating your app's logic in a spec file. You write the assertion where the code lives, with access to the real data: 

import { pass, fail } from 'scenetest'

export function ProfileForm() {
  const { data: profile } = useProfile()

  // Runs every render, with the actual value, at the actual moment
  pass('Profile available without loading state', profile !== undefined)

  if (!profile) return <CreateProfileForm />
  return <EditProfileForm profile={profile} />
}

In dev and test mode, these assertions report to a collector. In production, the Vite plugin strips them out entirely. Zero runtime cost.

Multi-context comparisons

The most powerful use case is comparing data across contexts. After a form submission, you might want to verify that the DOM, component state, React Query cache, and database all agree: 

onSuccess: (savedProfile) => {
  const domName = displayRef.current?.textContent
  const stateName = name.trim()
  const cacheName = queryClient.getQueryData('profile')?.name
  const dbName = getProfileFromDb().name

  pass('All contexts agree on name',
    domName === stateName &&
    stateName === cacheName &&
    cacheName === dbName
  )

  fail('Cache out of sync with database',
    cacheName !== dbName
  )
}

This runs inside your onSuccess callback, at exactly the moment when your mental model says everything should be in sync. If there's a bug where the state updates but not the cache, you'll catch it here. It means your tests are testing your application code, not your test helpers.

The Scene stays clean

Because assertions live in the application code, Scene files can focus purely on orchestration: 

scene('User updates their profile', async ([user]) => {
  await user.goto('/profile')
  await user.get('label[name=Name]').cousin('input').fill('New Name')
  await user.get('button', { name: 'Save' })
            .disabled(false)
            .then(button => button.click())
  await user.read('success!')
  // That's it. All the assertions fired automatically.
})

The person writing this Scene doesn't need to know about React Query, or localStorage, or what the component's internal state looks like. They just need to know what a user would do. The implementation experts write the assertions; the journey experts write the Scenes.

What we're really testing

Scenes test the user's experience: does the product work the way we intended?

Inline Assertions test the engineer's mental model: does the system work the way we think it works?

These are complementary questions. A Scene can pass while assertions fail – the user got the right outcome, but through a code path we didn't expect. Assertions can pass while a Scene fails – all our assumptions are correct, but the user can't actually complete the journey because of a UI problem.

Together, they give you a complete picture. You traverse your product along both axes, and you know not just that it works, but why.
