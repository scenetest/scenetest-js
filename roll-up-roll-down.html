Roll-up · roll-down — three format layers, two sides

The server rolls rows up into verb-envelopes and frames them onto a wire; the client unrolls them down back into schema-validated rows. Three layers, mirrored. SSE ⇄ WS only swaps the bottom one.

What you build = the two adapters, not the libraries. BUILD = your glue · USE = existing lib (partysocket, EventSource, TanStack DB — you already have these) · APP = userspace schema. partysocket/partyserver/TanStack DB are used, never rebuilt.

⇅ THE WIRE — this is all that SSE-vs-WS changes

L3 connection half · the offset/resume half is a separate, deferrable feature
SSE · EventSource USE — dev server today (“partysse”)
WS · partysocket USE ↔ partyserver — prod, hibernating on a DO
server emits ↓ into the wire↑ client reads from the wire
Both carry the identical protocol envelope (your “jsonl line”). Swap the wire → L1 and L2 never move; nothing above the Transport line notices.
Same three layers, three paths — “at which layer do you switch from your spec to theirs?”
Path L1 · row/schema L2 · verb/state L3 · wire/transport
A · native ▶ your types your RowOp projection your envelope + partysocket / SSE (no offsets v1)
B · DS lib StreamDB StandardSchema @durable-streams/state @durable-streams/client (HTTP/SSE, offsets)
C · bridge StreamDB schema @durable-streams/state partyserver WS + partysocket-as-their-transport

Read it as a U: down the server (rows → verbs → wire), across the wire, up the client (wire → verbs → rows). The two BUILD cells per side are the only glue you write — the emitter and the Transport adapter at L2/L3. Path A = own all three layers; B swaps all three for theirs; C keeps your L3 socket but adopts their L1+L2. The path choice is purely how far down the stack your spec reaches.
