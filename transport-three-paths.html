One primitive, three transports — choosing the path

The collection sync() seam is shared by all three; only what feeds it differs. One question decides the path — and it's about durability on reconnect, nothing else.

⌥ The fork that chooses

On reconnect, do you need incremental catch-up of missed messages — or is a fresh re-sync fine?

● fresh re-sync → Path A

Reconnect ⇒ resubscribe, get current state again. No offsets, no spec. Covers most dashboards.

● incremental catch-up → B / C

Replay exactly the missed messages by offset. Needs a state protocol — theirs (B) or theirs-over-your-socket (C).

What makes it “one primitive”

① Wire envelope

@scenetest/protocol events — the “jsonl line”. Every server emits it (SSE dev hub · partyserver WS). The format is the spec; in Path A it's yours.

② Transport interface

subscribe(onEvent, onStatus). Every client implements it (EventSource · partysocket). The wire is swappable; nothing downstream notices.

③ source → collection

createRunSource → runCollectionOptions.sync() → TanStack DB. Shared by all paths. Path A owns it; B/C swap it for StreamDB.

The primitive = ① + ② + ③. Path A is just: add a partysocket Transport + a partyserver emitter next to the SSE pair you already run. Path C later folds partysocket into @durable-streams/client instead, when incremental catch-up earns its keep.

▶ Moving ahead with Path A. It needs no spec but your own protocol envelope, reuses your entire Transport→createRunSource→collection stack, and gets hibernation from partyserver. The fork node stays the upgrade trigger: the day you need offset-based catch-up, B or C is a swap below the Transport line — userspace never changes.
